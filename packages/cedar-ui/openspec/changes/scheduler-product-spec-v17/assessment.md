# 任务日历 v1.7 适配评估

评估日期：2026-09-11

输入基线：产品《任务日历组件 · 交互设计 Spec》v1.7，以及当前 `src/scheduler` 实现、Demo 和公开 API。

## 结论

当前 Scheduler 足以继续作为底座，不建议替换为第三方日历。日期导航、分钟定位、拖拽/拉伸、全天区、当前时间线、多资源关联、组合筛选、冲突/容量/可用时间校验、自定义详情与编辑器等通用能力已经具备。

产品验收仍不能直接通过，但不应为了逐像素复刻 Spec 把出勤单和任务状态机加入基础组件。推荐把一个出勤单适配为一个 `SchedulerEvent`，任务列表通过 `event` 和 `editor` 插槽渲染。这样天然拥有整单边框、整单拖动和稳定重叠布局；任务的增删、标准工时求和、打卡与状态转换由业务表单完成。代价是单内任务不再各自拥有独立的纵向时间片，这项交互应优先请产品接受。

建议把范围分成两层：

- `Scheduler` 继续提供可复用的时间布局、资源关联、粗粒度权限、拖放事件和校验协议。
- 新增业务组合 Demo/容器实现出勤单、任务池、来源树、打卡记录和业务表单。不要把“站长、PowerGo、出勤单状态”等枚举写进基础组件。
- 只有两个以上业务都证明需要“一个视觉组包含多个独立时间事件”时，才考虑增加通用分组布局；当前阶段不增加 `layoutUnit`。

## Spec 内部需要先确认的冲突

下列内容在 v1.7 文本中存在不同版本的结论，开发前应以验收口径再确认一次：

1. 变更记录写明取消极端密度的“+N”，D3 仍写“可收敛为 +N”。最终采用可选 `overlapEventLimit`：默认完整展示，业务可在高密度页面启用，与月视图交互一致。
2. 变更记录写明聚焦只置顶并保持原宽，D12 仍写聚焦后展开到 `0.8W`。建议保持原宽，只调整 z-index。
3. D12 的宽度公式与验收摘要“每单元露出 `0.9W/K`”需要用 2、3、6 个重叠单元的视觉标注稿校验。
4. D7 说警示只用角标，v1.7 变更记录又要求“驳回待补为红色左竖条、无角标”。建议以后者为准。
5. D5 仍写待办/打卡 Tab，D10 已改成二级树，v1.7 又把打卡记录移入详情 hover。建议删除 Tab 方案，以“待办树 + 详情内打卡”为唯一方案。

## 最小模型与边界

基础组件只新增一个通用扩展点：`SchedulerEvent.metadata?: Record<string, unknown>`。Scheduler 对内容没有任何解释，只在新建、编辑、拖动和复制时保留一层独立副本。业务可以保存 `attendanceOrderId`、`typeId` 或其他关联键，又不需要污染基础类型。

推荐由业务适配器完成如下映射：

```ts
const event: SchedulerEvent = {
  id: order.id,
  title: order.tasks[0]?.name ?? "无主题",
  start: order.displayStart,
  end: order.displayEnd,
  resourceIds: [order.personId, order.deviceId],
  readonly: order.closed,
  metadata: { attendanceOrderId: order.id, typeId: order.type },
};
```

任务、打卡、技能、工时和状态仍保存在 `AttendanceOrder`。卡片插槽通过 ID 查询业务 store；编辑器提交业务对象后，再生成新的 Event。基础 Scheduler 不承担业务对象的深拷贝和持久化。

### 建议让产品接受的交互调整

| 原要求                                     | 建议实现                                                            | 原因                                               |
| ------------------------------------------ | ------------------------------------------------------------------- | -------------------------------------------------- |
| 单内每个任务都是独立时间块并由整单边框包围 | 一个出勤单一张日程卡，卡内按行显示任务                              | 保持整单拖动、重叠和权限模型简单稳定               |
| 拖任务到已有出勤单直接合并                 | 先选待办，再点目标日程的“加入任务”；拖到空白仍创建                  | 不扩展事件卡为复杂 drop target，触屏和键盘也能完成 |
| 所有冲突都在拖动后打开编辑框定位字段       | 拖动前后用 warning 提示；技能不符由业务保存钩子阻止并打开业务编辑器 | 基础组件不理解技能和表单字段                       |
| 人、设备各复制一个日程块并联动             | 同一个 Event 关联人和设备，切换展示维度；需要对比时使用资源时间线   | 避免重复实体和同步状态                             |
| 三列布局必须属于日历组件                   | 由页面布局组合任务池、资源树和 Scheduler                            | 三列工作台不是通用日历职责                         |
| 完成、休息、驳回是内置日程类型             | 业务类型映射到通用 metadata、appearance 和 readonly                 | 其他业务可定义自己的类型                           |

## 第三方组件可借鉴内容

| 组件                  | 值得吸收                                                                         | 不建议直接引入的原因                                               | 处理方式                                                                              |
| --------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| FullCalendar Standard | 外部拖入的 mirror/create 分离、eventAllow/constraint、开始/时长/资源分别控制编辑 | 资源时间线和资源列属于 Premium；引入其 DOM/状态机还要重做 Cedar UI | 参考 API 语义，为 Cedar 增加 drop proposal、能力解析器和约束诊断，不复制 Premium 代码 |
| TOAST UI Calendar     | `raw` 业务扩展、readonly、独立 border/background/dragBackground、模板与主题      | 没有本 Spec 需要的多维资源和 layoutUnit                            | 可在 MIT 许可下研究其公开实现；Cedar 增加通用 metadata/appearance，保留现有 core      |
| Syncfusion Scheduler  | 多层资源分组、多资源单 appointment、`allowGroupEdit` 的单数据多投影              | 商业组件，业务 UI 和 Cedar 体系差异大                              | 只采用“单实例、多投影”的数据原则和分组交互概念                                        |
| Bryntum Scheduler     | locked columns、ResourceTimeRanges、大数据时间轴、资源/事件颜色继承              | 商业授权且产品体量较重                                             | 借鉴资源时间段与滚动结构，不复制源码或依赖其运行时                                    |

当前 Cedar 已有的跨维度 AND/同维度 OR、组合资源行、纯 TypeScript 校验和 Vue 插槽比替换第三方更贴合本需求。第三方最适合作为交互和 API 设计参照。

## 风险

1. **把业务壳塞进基础 Scheduler。** 会让组件出现站长、设备待办、打卡等专属概念，其他业务无法复用。
2. **为单个需求过早引入布局组。** 会使碰撞、拖动、全天、跨日、多资源和无障碍全部增加双层状态；先采用一个出勤单一个 Event。
3. **只在按钮层做权限。** 拖拽和实例 `change()` 仍可能绕过限制；前端以 `readonly` 做粗粒度控制，细权限由业务编辑器和后端校验。
4. **同一出勤单重复数据。** 人与设备各复制一条会造成更新漂移；应保持一个实体，多处投影，交互按稳定 unit ID 联动。
5. **全量资源组合。** 当前交叉维度会生成笛卡尔积，大组织必须先筛选、分页或改为按需生成。
6. **前端校验被当成最终授权。** 技能、权限、容量、冲突和版本仍需后端原子校验。

## 建议验收数据集

至少固定以下场景作为 Demo 和回归夹具：

- 一张出勤单卡片显示 3 个任务，与另外 2 个出勤单和 1 个休息块重叠。
- 同一出勤单同时投影在人、设备两个选择结果中，hover、点击和详情联动。
- 2、3、6 个 Event 重叠，验证宽度、文字露出、置顶和失焦恢复。
- 拖待办到空白创建；选中待办后加入兼容出勤单；从业务编辑器移出最后一个任务。
- 技能不符硬拦截；时间重叠和饱和度超限只警示；异步期间权限撤销。
- 已完成出勤单使用实际打卡时间，只读、无左竖线、白色蒙版；休息斜纹底不透明。
- 00:00–24:00 完整轴默认定位 07:00，跨天/全天多段联动，弹窗关闭后恢复滚动位置。
