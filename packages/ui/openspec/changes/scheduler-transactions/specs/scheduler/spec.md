# Contracts

- `selectable` exposes selection-mode controls. `selectedKeys` / `defaultSelectedKeys` / `update:selectedKeys` use event IDs; shared resource projections select the same entity once. Selection mode disables card dragging and opens no editor. Exiting selection mode restores normal editing.
- `transaction(changes)` validates a nonempty list with at most one change per event ID and commits the full result once. Conflicts are checked on final state so swaps can succeed. Any invalid member rejects all members.
- `beforeTransaction(context)` runs once for all operation kinds and supersedes beforeChange when supplied. Without it, beforeChange continues to serve single changes. Multi-change operations with only beforeChange configured fail explicitly: they cannot safely persist a batch through a per-event hook. An application persistence hook must implement an atomic server request.
- Existing single-change events remain compatible. `transaction(value, context)` / `transaction-error(error, context)` describe batch/history operations; the transaction event also observes single changes. The action is change, undo or redo. Callbacks receive detached copies.
- `history` defaults false, `historyLimit` defaults 20. undo/redo use the same validation and persistence flow. Refused/failed operations do not change stacks; a new accepted change clears redo. Full snapshots preserve order when restoring removed events.
- In controlled mode only an exact parent-accepted value records history. External changes invalidate history; unaccepted proposals never enable undo. History is local, bounded and cleared when disabled, and is not collaborative server history.
- Batch toolbar actions move selected scheduled events one local day, add a chosen resource, or delete selected events. No action silently omits readonly/unscheduled selected items; invalid members reject the batch. Displayed selection excludes nonexistent IDs without mutating a controlled selection value.
